
### 4-Way Handshake 란??

- TCP 연결은 설정만큼이나 종료 과정도 매우 중요하다. 데이터 유실 없이 양쪽 둘다 안전하게 마무리 하기 위해서 4-Way 정상적인 종료 절차를 사용함!!

### 동작 과정

![](https://velog.velcdn.com/images%2Faverycode%2Fpost%2F3ec34c06-3d54-45f3-a6fb-bc5bfb415001%2F%E1%84%80%E1%85%B5%E1%84%89%E1%85%AE%E1%86%AF%E1%84%86%E1%85%A7%E1%86%AB%E1%84%8C%E1%85%A5%E1%86%B8-6%202.jpg)

- 1단계 : (클라이언트 FIN 전송) 
	- 연결 종료를 시작하는 측(클라이언트)는 더이상 보낼 데이터가 없음을 알리기 위해서 FIN 플래그가 1로 설정된 TCP 세그먼트를 서버에 보낸다. 
- 2단계 : (서버 ACK 전송) 
	- 서버는 클라이언트의 FIN을 수신하고 이를 확인했다는 의미로 ACK 세그먼트를 클라이언트에게 보낸다. 
	- 이떄 서버는 반 닫힘 상태가 된다. 
	- 클라이언트는 더이상 데이터를 보낼 수 없지만, 서버는 버퍼에 남아있는 데이터를 마저 보낼 수 있음. 
- 3단계 : (서버 FIN 전송)
	- 서버가 모든 데이터 전송을 마치고 소켓을 닫으면 FIN 세그먼트를 클라이언트에게 보낸다. 
	- 이후 서버는 마지막 ACK를 기다리는 상태로 전환
- 4단계 : (클라이언트 ACK 전송) 
	- 클라이언트는 서버의 FIN을 수신하고, 마지막 확인 응답으로 ACK 세그먼트를 서버에 보낸다. 


##### 종료 관련 패킷 식별 방법

- FIN 플래그가 1이다?? 이친구 연결 종료하려고 하는구나! 

> [!note] 참고
> 모든 연결이 4-Way HandShake으로 정상 종료 되는건 아님.
> 네트워크 오류나 애플리케이션 강제 종료 등 비정상적으로 중단될 수 있음. 


### RST 패킷

- TCP RST 패킷은 정상적인 4-Way Handshake를 생략하고 연결을 즉시 종료하는데 사용.
- RST가 송수신 되면 버퍼에 남아있는 데이터는 모두 폐기. 
- 연결에 할당된 자원은 즉시 해제. 
- 비정상적인 종료방식이다!

### 어떤경우에 RST 패킷을 전송할까??

- 닫힌 포트로 연결을 시도할때
	- 서버에서 리스닝 하고 있지 않은 포트로 SYN 패킷이 도착했을 때, 서버는 RST를 보내서 연결 불가능함을 알린다. 
- 존재하지 않는 연결에 대한 패킷 수신
	- 호스트가 재부팅 되어서 연결상태를 모두 잃어버린 경우
- 애플리케이션의 강제 종료 

### 갑작스러운 네트워크 장애 감지 

- 라우터 고장이나 케이블 단선과 같이 조용하게 혼자 실패하면 양측은 FIN, RST 패킷을 교환할 수 없음. 
- 이 경우에는 살아남은 쪽의 연결은 좀비연결이 되어버림. 
- 이 상황을 처리하는 매커니즘이 있음.

- 재전송 타임아웃
	- 한쪽에서 데이터를 보냈는데 ACK를 받지 못하면 데이터를 여러번 재전송한다. 
	- 그랬는데도 실패하면 연결이 끊어진 것으로 간주하고 타임아웃 처리한다. 
- TCP Keep-Alive 메커니즘
	- 운영체제는 아무런 데이터 교환이 없는 유휴 상태의 연결에 주기적으로 패킷을 보낸다. 
	- 만약 연결이 잘 되어있다면 ACK로 응답할 것. 
	- 만약 여러번 응답이 없으면 운영체제는 연결이 끊어졌다고 판단하고 강제로 종료.
