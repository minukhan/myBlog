
### HTTP가 Stateless로 설계된 이유.

- 단순한 서버 설계. 
- 웹 서버는 모든 클라이언트의 방문 기록을 메모리에 저장할 필요가 없으므로, 막대한 동시 접속자를 처리할 수 있음. 
- 웹의 폭팔적인 성장에 결정적인 역할을 함. 

### 근데 쇼핑카트와 같은 실제 웹 애플리케이션은 상태 유지가 필수.

- 이는 Stateless한 HTTP위에 쿠키, 세션을 이용해서  연결을 하지 않아도 연결한것처럼 동작할 수 있게끔 했음. 


###  Connectionless(연결 없는거 UDP) 문제??

- HTTP 자체는 연결을 유지하는 TCP를 사용했음.
- 그러나 HTTP/1.0에서는 연결을 하고 끊는 방식으로 동작해서 사실상 매번 연결하는 오버헤드가 컸다. 

- 그래서 나온 전략이 HTTP Keep-Alive (지속적 연결)
- HTTP/1.1부터 기본값이 되었다. 
- 하나의 TCP연결을 재사용해서 여러개의 HTTP 요청을 보낼 수 있도록 허용한다. 
- 반복적인 TCP, TLS 핸드셰이크를 피함으로써 시간을 줄임. 

### TCP Keep-Alive와 HTTP Keep-Alive

- 두 용어는 이름이 비슷하여 혼동하기 쉽지만, 완전히 다른 계층에서 다른 목적으로 동작하는 별개의 메커니즘

##### HTTP Keep-Alive (애플리케이션 계층, Layer 7)

- 성능 최적화가 목적
- 하나의 TCP 연결을 통해 요청/응답을 처리해서 연결 설정에 드는 지연 시간을 줄인다. 
- 서버는 설정된 타임아웃 동안 추가 요청을 기다리며 TCP 연결을 열어둔다. 

#### TCP Keep-Alive (전송 계층, Layer 4)

- 주된 목적은 연결 상태 관리 및 정리. 
- 아무런 데이터 교환이 없는걸 작은 프로브 패킷을 보내서 여전히 살아있는지 확인. 
- 이를 통해서 좀비 연결을 감지 정리하는 동작.
