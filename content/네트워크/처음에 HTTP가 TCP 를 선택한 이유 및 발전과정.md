
### 처음에 HTTP가 TCP 를 선택한 이유??

- 월드 와이드 웹의 근간을 이루는 HTTP는 설계 초기부터 TCP를 전송 계층 프로토콜로 채택했음. 
- 웹 페이지를 구성하는 HTML 문서, 이미지 등 하나의 비트라도 손상되거나 유실되면 페이지 깨지거나, 기능이 마비되니까 TCP를 선택. 
- 데이터의 완전한 전송이 필수적이였다. 
- TCP 덕분에 개발자들은 데이터 유실이나 뒤바뀜 이런걸 걱정할 필요가 없이 애플리케이션 로직만 집중할 수 있었음. 


### 그 후..

- TCP의 신뢰성은 강력했지만 그 자체로 성능 한계를 불러일으킴
	- 연결 설정 오버헤드 
		- 초기에는 웹 페이지에 포함된 모든 개별 자원들을 요청할 떄마다 새로운 TCP연결을 해버림
		- 각 연결마다 3-way Handshake 과정이 반복되면서 상당한 지연시간이 발생. 
	- HTTP/1.1 에서 지속연결 기능이 도입되었음. 
		- 이는 하나의 TCP 연결이 설정되면 여러개의 HTTP 요청과 응답을 동일한 연결을 통해서 처리할 수 있도록 허용해줬다. 
	- HTTP/2 등장!! 
		- 성능 개선을 위한 다음단계는 HTTP/2에서 도입한 멀티플렉싱!
		- 하나의 TCP 연결 내에서 여러개의 독립적인 논리적 스트림을 만들어서 여러 요청과 응답이 동시에 병렬적으로 처리될 수 있도록 하였다. 
		- 근데 여기서도 큰 문제가 생김! [[HOL Blocking]] 문제가 발생하는데  
		- 이 문제는 순서를 지키느라 한 마디 놓치면 뒤에것도 다 멈추게 된다!

	- HTTP/2가 직면한 HOL Blocking 문제는 TCP 프로토콜 자체의 근본적인 특성에서 비롯됨. 
	- 그래서 현실적으로 TCP를 수정하는건 불가능이라고 판단했다!
	- 그래서 다른 접근법으로 UDP가 나오게 됐다!
	- 기능이 거의 없어서 대부분의 네트워크에서 자유롭게 통과가 가능, 커널 수정없이 애플리케이션 레벨에서 새로운 기능을 자유롭게 구현하고 배포할 수 있는 백지상태라 좋았음. 

- 그래서 나타난게 QUIC(Quick UDP Internet Connections)
	- UDP 위에 구현된 새로운 전송 프로토콜임
	- QUIC은 UDP 위에다가, TCP가 가진 중요한 기능들을 **다시 직접 구현**

### 그러면 QUIC은 어떻게 TCP 문제를 해결했나??

- QUIC은 UDP의 유연성을 활용하여 TCP의 고질적인 문제들을 해결!

- HOL Blocking 제거
	- 각 스트림은 전송계층에서부터 완전히 독립적이다.
	- 각 스트림은 고유한 흐름제어와 순서 번호 체계를 가져서 손실이 발생해도 영향이 없게끔 설계했다고 함. 
- 연결시간 단축 (1-RTT, 0-RTT)
	- QUIC는 전송계층의 핸드셰이크와 암호화를 담당하 TLS1.3 핸드셰이크를 하나의 과정으로 통합했다. 
	- 그래서 왕복시간(RTT)가 1회로 줄어들었음. 
	- 원래는 TCP, TLS 등을 하면서 2~3번 왕복해야했음.
	- 이게 또 좋은게 다시 같은 서버에 접속할때면, 예전에 썼던 암호화키를 기억하고있어서 또 왔다갔다 안해도 됨.
