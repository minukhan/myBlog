
### 둘다 전송계층이다. 

- 전송계층은 네트워크 핵심적인 역할을 수행. 
- 특정 애플리케이션에서 다른 컴퓨터로 정확하게 전달하는 다리역할을 한다. 
- 이를 위해서 전송 계층은 포트번호라는 주소체계를 사용해서 동일한 IP 주소를 가진 컴퓨터 내에서도 여러개의 통신을 할 수 있도록 구분한다. 
- 이때 사용하는 프로토콜이 TCP, UDP임. 

### TCP

- 데이터 전송의 신뢰성을 최우선으로 고려해서 설계된 프로토콜. 
![](https://i.imgur.com/Bpt8wxf.png)

##### 특징 

- 연결 지향 서비스 
	- 데이터를 전송하기 전에 송신자와 수신자 간의 연결을 설정. 
	- 이떄 3way Handshake 과정이 일어남.
	- 종료시에도 4-way Handshake 절차로 안전하게 해제. 
	- 이처럼 연결 상태를 유지하고 관리하기 떄문에 TCP는 상태기반 프로토콜

- 신뢰성 있고 순서가 보장되는 전달
	- 데이터가 손상없이, 중복없이 잘 전달되는점.
	- 어떻게 잘 손상없이 중복없이 잘 전달될까?? 
	- TCP는 데이터조각(세그먼트)마다 순서 번호를 부여하고, 수신측은 데이터를 받을때마다 확인 응답(ACK)를 보내서 알린다. 
	- 만약 중간에 유실되거나 손상되면 송신측은 다시 재전송. 

- 흐름제어 및 혼잡제어
	- TCP는 내장된 제어 메커니즘을 통해서 안정적으로 통신 지원한다. 
	- 총 3가지 제어 기능이 있다. 
	- 흐름제어 
		- 수신측의 데이터 처리 속도를 고려해서 전송량을 조절함.
		- 그러면서 버퍼 넘치는걸 방지한다. 
		- 수신자가 내 현재 Buffer 상태를 전달해주면
		- 송신자는 그걸 보고 조절을 하는것! 
	- 혼잡제어
		- 지수적으로 빠르게 올린다고 함 사용률을 최대한 끌어올리려고.
		- 그떄 임계점에 도달하면 조절하기.
		- 혼잡한 상황을 감지해서 속도를 조절. 
		- 얘는 송신자의 Buffer 를 보는게 아니라 네트워크 상황을 보는것. 
		- 라우터가 버퍼 오버플로우로 패킷을 버리면 → 송신자는 타임아웃이나 **중복 ACK**을 통해 손실을 감지.
		- RTT(왕복 지연)가 커지면 → 네트워크 혼잡이 증가했다고 추측한다. 
		- 그러면 이제 송신자가 혼잡하네?? 속도 줄이기. 
		- 네트워크 전체의 안정성을 유지하는 기능. 
	- 오류제어 
		- 잘못됨을 감지하는 경우? 
			- 송신 측이 ACK(긍정응답)을 받지 못함
			- 중복된 ACK를 받는다.
			- 수신 측이 NACK(부정응답)을 보냄

		- 데이터가 유실되거나 잘못된 데이터가 수신되었을 경우 대처하는 방법
			- 1. Stop-and-Wait ARQ
				- 한 번에 1개 보내고 ACK 기다림. ACK 없으면 타임아웃 후 재전송.
				- 단순, 구현 쉬움.
				- **RTT가 크면 효율↓** (회선 놀림). 시퀀스 번호 1bit로도 충분.
			1. Go-Back-N (GBN)
				- 윈도우 크기 N만큼 **파이프라이닝**. 손실 감지 시 **해당 손실 지점부터 전부 재전송**.
				- 높은 처리량.
				- 하나 잃으면 그 뒤도 **모두 재전송** → 낭비.
			2. Selective Repeat (SR)
				- **잃은 것만 선택 재전송**. 수신측은 **버퍼링** 후 **순서 재조립**.
				- 대역 효율↑, 지능적.
				- 단점은 수신 측 버퍼의 데이터가 순차적이지 않다 그래서 수신 버퍼가 별도로 필요하다고 함!

### UDP

- 신뢰성보다 속도와 효율성을 중시하여 설계된 프로토콜임. 

##### 특징

- 비연결 서비스
	- UDP는 데이터를 보내기 전에 연결을 안함. 
	- 귀찮은 3 way-Handshake 과정이 없음.
	- 송신자는 데이터그램이라는 독립적인 패킷으로 만들어서 네트워크로 전송

- 비신뢰성
	- 데이터의 도착, 순서, 무결성을 전혀 보장하지 않는다. 
	- 애플리케이션이 준 데이터를 그냥 데이터그램으로 감싸서 IP계층에 전달하는 최소한의 역할만 수행한다. 
	- 패킷이 유실되거나 순서가 바뀌어도 바로 잡으려는 시도를 안함. 
	- 오류 제어는 애플리케이션 계층에서 해라! 무책임한놈!

- 최소주의와 속도
	- 가장 큰 장점은 연결 설정, 확인 응답, 순서 재조립, 흐름 및 혼잡제어 같은 복잡한 메커니즘 없다는 점.
	- 그래서 오버헤드도 적고 속도가 매우빠르다!!

- 멀티캐스트 및 브로드캐스트 지원
	- TCP는 일대일만 지원하지만 UDP는 일대다, 브로드캐스트 통신을 지원한다. 
	- DHCP와 같은 서비스 검색 프로토콜이나, 실시간 미디어 스트리밍 서비스에서 필수!


#### 참고

- TCP 와 UDP 사이의 선택은 단순히 속도와 신뢰성 간의 트레이드 오프뿐만 아니라, 
- 신뢰성 보장의 책임을 어디에다 둘것인지에 대한 아키텍처 결정. 
- TCP를 선택한다면 운영체제 커널에 책임을 둔다.
- UDP를 선택하면 애플리케이션 개발자에게 책임을 둔다. 
- 이러한 유연성은 실시간 게임, 특정 분야에서 여겨지고있음. 


### 각각 그러면 어디서 사용되고있어??

##### TCP 

- 웹 브라우징 
	- 웹 페이지를 구성하는 HTML, 이미지, 스크립트 등 하나의 데이터라도 유실되면 이상해짐. 

- 파일 전송
	- 문서나 프로그램을 다운로드할때 파일이 손상되면 안되니까 신뢰도가 있는 TCP 사용
    
- 이메일(SMTP, POP3, IMAP)
	- 이메일 내용이 중간에 사라지거나 순서가 뒤바뀌면 안되니까 TCP 사용

- 채팅 
	- 메시지가 순서대로 전달되어야하고 누락도 없어야하니까 TCP 사용

##### UDP

- 실시간 스트리밍(영상/음성)
	- 라이브 방송이나 동영상 스트리밍, 인터넷 전화 등은 화질 저하나 음성 끊김이 있더라도 지연없이 실시간으로 데이터를 빠르게 주고받는게 중요하다. 

- 온라인 게임 
	- 플레이어의 움직임이나 스킬같은 데이터를 최대한 빠르게 서버와 다른 클라이언트에게 전달해야하니까!

- DNS (Domain Name System)
	- 도메인 이름을 IP주소로 변환하는 과정이 필요하다함.
	- 간단한 요청과 응답으로 이루어져 있어서 신뢰성보다 속도가 더 중요하다고 함. 

- DHCP (Dynamic Host Configuration Protocol)
	- IP 주소를 할당받는 프로토콜로 신속한 처리가 중요
	- TCP 연결을 맺기 전에 동작해서 UDP를 사용한다.

### 체크섬이 뭐야??

- 데이터가 전송 과정에서 잡음이나 기타요인으로 손상되어있는지 확인하는 단순한 검출 메커니즘이다. 
- 처음에 송신자가 데이터 블록을 전송할때 짧은 고정 크기의 값을 계산해서 데이터와 함께 보낸다. 
- 이때 수신자는 동일한 알고리즘으로 체크섬을 계산. 같다? 어 너 잘 왔구나! 다르다? 너 변질됐네? 손상!

- 여기서 오류는 검출한다 하지만, 오류를 어디서 잘못됐는지 알 수 없음.
- 바로잡을 수 없음. 이 한계 때문에 TCP와 같은 신뢰성 있는 프로토콜은 오류가 검출되면 별도 재전송 메커니즘을 필요로 하는 것. 

### TCP 랑 UDP는 체크섬 써?? 

- TCP/UDP 헤더는 모두 16비트 체크섬 필드를 포함하여 이 메커니즘을 수행함. 
- UDP의 경우에는 IPv4 환경에서 체크섬 계산이 선택이였으나 실제로는 모든 구현에 체크섬을 사용해서 IPv6 환경에서는 필수가 되었다. 

### 어 왜 TCP는 체크섬 쓰는거야? 이미 신뢰성 보장된거 아니야??

- TCP는 신뢰성 있는 프로토콜이라고 하니까 안써도 되겠구나 싶지만, 이건 패킷이 누락되거나 순서가 잘못되면 그걸 바로잡아주는 신뢰임! 
- 잘못된 패킷이 들어오는 그런 검증해주는건 checkSum 을 이용해서 감지한다!!!

### 그래서 TCP는 어떻게 신뢰있는 연결을 하니?? 

- 순서 번호
	- TCP는 데이터 스트림의 고유한 순서 번호를 할당한다.
- 확인 응답
	- 수신자는 데이터를 성공적으로 수신했음을 알리는 ACK 패킷을 보냄. 
- 오류 감지(Checksum)
	- 체크섬을 통해서  수신된 세그먼트의 데이터 손상 여부를 확인한다. 
- 재전송
	- 정해진 시간 내에 ACK를 받지 못하면 유실된걸로 간주하고 다시 전송. 


### 브라우저 - 서버 간 프로토콜 협상

- 브라우저가 특정 서버와 통신할 때, 어떤 프로토콜을 사용할지는 정교한 협상 과정을 통해서 결정된다.
