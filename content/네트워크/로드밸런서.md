
### 로드밸런서가 뭐야??

- 로드밸런서는 말 그대로 부하를 분산시키는 장치, 소프트웨어 기술
- 클라이언트로부터 오는 많은 요청을 여러대의 서버로 분산시켜주는 역할. 
- 하나 서버에 과부하 걸리는걸 방지, 처리량을 높임
- 만약 일부 서버에 장애가 발생하더라도 서비스 중단 없이 안정성을 유지할 수 있게 해준다. 
### L4 로드밸런서, L7 로드밸런서의 차이

- OSI 7계층중에 어느 계층의 정보를 기반으로 트래픽을 분산하느냐에 따라 종류가 나뉨. 

##### L4 로드밸런서

- 4계층 전송계층에서 동작한다.
- 패킷에 헤더에 있는 IP주소와 포트번호를 기반으로 트래픽 분산.
- 어디서 온 요청이 어디로 가는지 판단.

- 패킷의 내용을 들여다보지 않고 IP와 포트정보만 확인해서 속도가 빠름.
- 구조가 단순하고 설정이 용이.
- 구체적인 내용을 인지하지 못해서 정교한 부하 분산은 불가.

##### L7 로드밸런서

- 7계층 애플리케이션계층에서 동작
- 패킷의 내용까지 분석해서 더 상세하게 트래픽을 분산

- 정교한 분산
- 보안기능
- 성능 부하


### 로드밸런서 알고리즘

- 라운드 로빈
	- 들어오는 요청을 순허대로 서버에 하나씩 할당. 
- 가중치 기반 라운드 로빈
	- 성능이 좋은 서버에 더 많은 요청이 할당되도록 할당. 
	- 서버의 성능이 다를때 사용
- 최소 연결
	- 현재 서버의 상황을 보고 요청 연결수가 가장 적은 서버에게 요청을 보낸다. 
- IP 해시
	- 클라이언트의 IP주소를 해싱해서 특정 서버로만 요청을 보냄. 
	- 항상 동일한 서버에 접속하게 됨. 
- 최소 응답시간
	- 서버의 연결 수와 응답시간을 모두 고려해서 가장 빠르고 부하가 적은 서버에게 요청을 보냄.

### 로드 밸런싱 대상이 되는 서버가 장애가 발생해서 접속이 안된다면?? 

- 로드 밸런서는 해당서버로 요청을 보내면 안됨! 그러기 위해서 하는게 헬스체크!

- 헬스체크 
	- 로드밸런서가 주기적으로 서버들의 상태를 점검하는 과정
	
	- 주기적인 신호 전송(TCP Keep-Alive 랑유사하네)
	
		- 확인 방법 : 
			- L3 체크 : 서버의 IP 주소로 ping을 보내서 응답이 오는지 확인. 
			- L4 체크 : 서버의 특정 포트로 TCP 연결을 시도. 
			- L7 체크 : 실제 애플리케이션에 요청을 보내서 정상적인 응답이 오는지 확인함. 

	- 장애 판단 및 조치
		- 서버가 정해진 시간 내에 응답하지 않거나 비정상 응답을 반복적으로 보낸다?? 얘 죽었다! 판단.

	- 트래픽 제외 및 복구
		- 비정상으로 판명된 서버는 로드밸런싱 대상에서 즉시 제외.
		- 이후 죽은 서버의 상태를 계속 확인하다가 정상적인 응답이 오면 정상 상태로 복구시켜서 포함시키기도 함. 


### 로드밸런서를 사용하지 않고 DNS를 활용해서 유사하게 로드밸런싱을 하는 법


- 로드밸런서가 없더라도, **DNS 서버**의 기능만으로 간단한 분산 효과를 낼 수 있다.
	- DNS Round Robin (DNS 라운드 로빈)
- DNS를 이용해서 유사한 부하 분산 효과를 얻을 수 있음.
- 서버의 상태를 확인하지 못한다는 단점. 그리고 정교한 제어가 불가능함. 
- 무중단 서비스가 필수적인 고가용성 시스템 보다는 단순 트래픽 분산이 목적인 경우에 적합.
- 하나의 도메인에 **여러 개의 IP 주소를 등록**할 수 있음.

```
example.com → 203.0.113.1
example.com → 203.0.113.2
example.com → 203.0.113.3
```

|클라이언트 요청 순서|DNS 응답 (IP)|
|---|---|
|1번째|203.0.113.1|
|2번째|203.0.113.2|
|3번째|203.0.113.3|
|4번째|203.0.113.1 (다시 처음으로)|
- 간단하고 비용이 적게들어서 좋음.
- 그러나 서버 상태를 인식할 수 없어서 서버가 죽어있어도 IP를 계속 응답하게 된다.
