
### 사용자가 브라우저 주소창에 www.github.com을 입력하면??

##### 1. 사용자 입력 및 URL 파싱 

- 사용자가 주소를 입력하면 브라우저는 이 문자열을 파싱한다. 
- 현대 브라우저는 별도의 프로토콜이 명시되지 않으면 https 를 사용한다. 
- 브라우저는 프로토콜(`https`), 호스트 이름(`www.github.com`), 그리고 경로(기본값 `/`)를 식별

##### 2. DNS 조회 

- 브라우저는 서버와 통신하기 위해서 IP 주소를 알아야한다. 
	- 로컬 캐시 확인 
		- 브라우저는 자신의 캐시, 운영체제의 캐시, 로컬 파일을 순서대로 확인하면서 이전에 조회한 기록이 있는지 확인한다. 
	- 재귀적 DNS 쿼리
		- 만약 로컬에서 찾지 못했다면 OS는 설정된 DNS 서버에 재귀적 쿼리를 보낸다. 
	- 반복적 쿼리
		- 재귀적 쿼리를 받은 DNS 서버는 ROOT DNS 서버부터 시작해서 .com TLD(최상위 도메인) 서버를 거쳐서 최종적으로 github.com의 권한 있는 네임 서버에 도달할 때까지 반복적으로 쿼리를 수행한다. 
	- 응답 및 캐싱 
		- 최종적으로 얻은 IP주소는 브라우저에 전달된다. 
		- 각 단계에서 조회 결과는 다음 조회를 위해 캐싱됨.

##### 3. TCP 연결 설정. 

- 브라우저는 DNS 조회를 통해서 얻은 IP 주소와 https의 표준 포트인 443을 사용해서 서버와 TCP 연결을 시작한다. 
- 이때 3-Way HandShake가 수행된다. 

##### 4. TLS 핸드셰이크

- TCP 연결이 완료되었다면 https 통신을 위해서 암호화된 채널을 설정하는 TLS 핸드셰이크가 진행됨. 
- 클라이언트와 서버는 인증서를 교환하고 암호화 매개변수를 만듬. 
- 이후 모든 데이터를 암호화하는 데 사용할 세션 키를 생성한다. 

##### 5. HTTP 요청

- 암호화된 연결 위로, 브라우저는 서버에 HTTP 요청을 보낸다. 
```
GET / HTTP/2
Host: www.github.com
User-Agent: [브라우저 정보]
```

- 이런식으로 호스트의 루트, 리소스 방식(GET) 등을 정해서 요청함. 
- 현대 웹에서는 HTTP/2 or HTTP/3를 주로 사용한다. 

##### 6. 서버 측 처리 

- GitHub의 인프라에 도달한다. 
- 가장 먼저 로드 밸런서가 요청을 받아서 TLS 연결을 종료한다. 
- 수많은 백엔드 서버 중 하나로 요청을 전달. 
- 요청을 받은 웹 서버(NginX)는 정적 자원을 직접 처리. 동적 컨텐츠 요청을 웹 어플리케이션 서버로 전달
- 애플리케이션 서버는 GitHub 홈페이지를 구성하는 비즈니스 로직을 실행. 


##### 7, 8. HTTP 응답 + 브라우저 렌더링 

- 애플리케이션 서버가 생성한 HTML은 다시 웹 서버를 통해서 HTTP 응답 메시지로 포장되어 브라우저에게 전달. 
- 브라우저는 수신한 HTML을 파싱해서 DOM 트리를 구축. 
- 태그에 맞춰서 화면 뿌려주기. 


### DNS 조회로 얻은 IP 주소는 실제 어떤걸 가르키나??

- 대규모 서비스의 경우 DNS 조회로 얻은 IP주소는 단일 물리적 서버를 가리키지 않는다. 
- 해당 서비스 인프라의 정문 역할을 하는 가상 엔드포인트를 가리킨다. (로드밸런서, CDN 엣지)
- 그러니까 실제 특정 기계의 물리적 주소가 아니라, 서비스의 논리적 진입점을 나타내는 추상화된 주소를 말함. 
- DNS는 사용자를 이 서비스의 올바른 진입점으로 안내하는 역할을 한다. 


### 웹 서버와 웹 애플리케이션 서버의 차이점

![](https://i.imgur.com/rLK2bSU.png)


- 웹 서버 (Web Server, 예: Nginx, Apache)
	- 주된 역할은 HTTP 요청을 받아서 정적 콘텐츠를 제공하는 것. 
	- 디스크에 저장된 그대로 제공되는 파일(HTML, CSS, 이미지) 를 의미한다. 
	- 리버스 프록시, 로드 밸런싱, TLS 종료점 등의 역할을 수행한다. 
	- 동적 컨텐츠 요청을 애플리케이션 서버로 전달하는 관문 역할. 

- 웹 애플리케이션 서버 (Web Application Server, 예: Tomcat, Gunicorn, Node.js)
	- 내가 흔히 개발하는 Backend 서버 
	- 주된 역할은 비즈니스 로직을 실행해서 동적 컨텐츠를 생성.
	- 데이터베이스, 메시징 큐 같은걸 이용해서 맞춤형 응답. 

- 협력 구조 
	- 원래는 웹 애플리케이션 서버가 웹 서버 역할도 하면서 동시에 수행했음. 
	- 고성능 아키텍처에서는 웹 서버가 애플리케이션 서버의 앞단에 위치. 

### 식별자 용어

- URI (Uniform Resource Identifier)
	- 리소스를 고유하게 식별하는 문자열. 
	- URL과 URN은 모두 URI의 하위 집합
	- URI는 리소스를 어떻게 찾을 수 있는지에 대한 정보를 반드시 포함하지는 않음.
- URL (Uniform Resource Locator)
	- 우리가 흔히 웹 주소라고 부르는 대부분의 주소가 여기에 속함.
	- 리소스를 식별할 뿐만 아니라, 리소스의 위치와 접근 방법(프로토콜)까지 명시하는 구체적인 URI
- URN (Uniform Resource Name) 
	- 리소스의 위치와 무관하게 영속적인 이름으로 리소스를 식별하는 URI

> [!note] 정리
> 한 사람의 이름 : URN
> 한 사람의 집주소 : URL
> URN + URL = 개인정보 = URI
