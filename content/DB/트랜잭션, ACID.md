
### [[트랜잭션(Transaction)]]개념


### [[ACID]]원칙

- 원자성
	- 모두 되거나 모두 안되거나.
- 일관성 
	- 트랜잭션이 성공적으로 완료되었다면 DB는 완전한 상태가 되어야한다.(사전의 모든 규칙을 만족하는 상태)
- 고립성
	- 다른 트랜잭션이 동시에 실행될때 서로 영향이 없어야함. 
- 지속성
	- 트랜잭션이 성공하면 그 변경사항은 DB에 영구적으로 기록되어야 함. 
	- 이후에 장애가 발생해도 커밋됐다면 손실 되지 않아야함. 


### DBMS는 어떻게 지속성을 보장하나? 

- 핵심 과제는 휘발성인 메인 메모리 RAM과 영구적이지만 느린 디스크와의 차이를 줄이는 것. 
- DBMS는 성능 저하 없이 변경된 사항을 영구 저장소에 안전하게 도달하도록 보장해야함. 


- 핵심 메커니즘 : WAL(Write-Ahead Logging)

	- DBMS는 데이터 변경 사항을 실제 데이터 파일에 적용하기 전에 변경에 대한 기록을 먼저 디스크의 순차적인 로그 파일에 기록함. 
	- 트랜잭션이 커밋될 때, DBMS는 해당 트랜잭션에 대한 로그 레코드가 영구적인 로그파일에 안전하게 기록되었음을 보장. 
	- 이 방식이 빠른 이유는 흩어져 있는 데이터 파일에 찾아서 쓰고 하는거보다 하나의 로그 파일에 순차적으로 빠르게 기록함. 

- 시스템 장애가 생긴다면??

	- 만약 트랜잭션이 커밋된 후 시스템이 충돌하고, 아직 데이터 페이지가 디스크에 기록되지 않았다면 WAL이 복구에 사용된다. 
	- 시스템이 재시작될 때, 데이터베이스 복구 프로세스는 WAL을 읽는다. 
	- 로그에 기록되어있는데 데이터 파일에 반영이 안된것들을 다시 실행해서 지속성을 보장. 

### 트랜잭션은 언제 사용해야해??

- 하나의 논리적 작업을 완료하기 위해서 두개 이상의 데이터 수정이 필요한 경우.
- 이들이 모두 성공하거나, 실패해야만 데이터의 일관성이 유지되는 경우 사용한다. 

### 읽기에는 트랜잭션을 걸지 않아도 될까??

- NO 
	- 읽기작업에도 사용해야한다고 함. 
	- 여러개의 select 문을 수행할떄 중간에 값이 바뀌어버리면, 결과가 달라짐. 
- 그래서 이걸 어떻게 하는게 좋을까??
	- READ ONLY 라는 옵션이 있음.
		- DBMS는 이 트랜잭션이 데이터를 변경하지 않는다고 인지하고 불필요한 Lock, 롤백 정보 기록같은 오버헤드를 줄일 수 있음. 
	- Spring 에서는 @Transactional(readOnly = true) 어노테이션을 사용하면 
	- Hibernate의 '더티 체킹(dirty checking)' 메커니즘을 비활성화하는 등의 추가적인 최적화가 이루어진다. 


- 약간 오래된 데이터를 읽어도 괜찮은 조회 경우에는 안해도 됨. 
- 트랜잭션 하나가 다 오버헤드니까 줄이는것도 좋음. 
- 데이터베이스의 기본 자동커밋 동작으로도 충분하다!
