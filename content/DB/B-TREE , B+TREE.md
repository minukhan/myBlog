
### B-TREE가 뭐야?? 

-  B-Tree는 이진 탐색 트리를 일반화 함.
- 하나의 노드가 두 개 이상의 자식을 가질 수 있도록 한 자가 균형 탐색 트리.
- 각 노드는 여러개의 값을 저장할 수 있음!
![](https://i.imgur.com/DI59tGD.png)


- 이런식으로 하나의 노드 안에 여러개의 값을 저장.
 ![](https://i.imgur.com/p1WjP7u.png)


### B+TREE가 뭐야??

- B-TREE 의 변형!
- 데이터베이스 인덱스를 위해 더욱 특화된 구조를 가진다. 

- 데이터의 저장 위치 :
	- 데이터는 오직 리프 노드에만 저장됨. 
	- 내부 노드는 리프노드를 찾아가기 위한 표지판 역할을 하는 키값만 저장. 

- 연결된 리프 노드 :
	- 모든 리프노드가 양방향 연결리스트로 연결되어있음.
	- 서로 연결되어있어서 순차적인 데이터 탐색이 효율적이다. 
![](https://i.imgur.com/enzAeYR.png)

- B+TREE는 데이터 베이스의 가장 흔한 접근인 특정 값 조회, 범위 스캔에 최적화 된 형태.
- 데이터가 리프노드에만 존재하므로 더 많이 쪼개서 가리킬 수 있다고 함. 

```
WHERE ID BETWEEN 100 AND 200
```
- 이거와 같은 범위 스캔시, 
- B-Tree처럼 트리를 오르내릴 필요 없이 ID 100을 찾은 후 연결 리스트를 따라 ID 200까지 선형적으로 탐색하면 되므로 매우 효율적임. 


### 왜 현대에 B+TREE가 주로 사용될까??

- 범위 스캔 속도가 말도안되게 빠르다!
- 내부노드에 키만 저장해서 노드당 더 많은 자식 포인터를 가질 수 있어 트리의 높이가 줄어들어 빨라짐. 
- 모두 리프노드에 있어서 동일한 높이를 탐색. 

- 그러나 B-TREE가 더 빠를 수 있음. 만약 젤 가까운 곳에 있었으면 빠르게 찾는거임. 
- 근데 일반적으로는 B+TREE가 더 빠르므로 B+TREE를 사용한다. 

### 왜 DB에서 레드블랙트리가 아니라 B-TREE/B+TREE를 사용하나? 

- 디스크 기반 자료구조를 설계할때 목표는 디스크 접근(I/O) 횟수를 최소화하는 것. 
- 주 메모리(RAM) 접근 속도는 디스크 접근 속도보다 훨씬 빠름. 

- 근데 여기서 이진트리는 각 노드가 2개의 자식 노드밖에 가질 수 없어서 트리의 깊이가 깊어질 수 있음. 
> 여기서 노드는 디스크에 저장되어있는데 이떄 노드의 깊이만큼 타고 갈떄마다 디스크를 읽어오는 것임. 그래서 깊이가 깊어지면 디스크를 많이 읽어와야해서 속도가 느려지는 것. 

- 여기서 B-TREE 같은 자료구조는 디스크 I/O를 최소화 함. 트리의 높이를 낮추고, 하나의 디스크 블록에 많은 데이터를 저장하기 때문에 I/O 횟수가 적어진다. -> 속도 빠르다. 

### 오름차순으로 정렬된 인덱스가 있다고 할 때, 내림차순 정렬을 시도할 경우 성능이 어떻게 될까요? B-Tree/B+Tree의 구조를 기반으로


- 논리적으로 B+Tree 인덱스는 정렬되어 있으므로 양방향으로 탐색이 가능. 
- 정방향 스캔, 역방향 스캔 둘다 문제없이 수행한다. 

> 근데 MySQL의 InnoDB와 같은 많은 구현체에서 역방향이 정방향보다 약간 느리다고 함. 

#### 왜?? 

- 1. 페이지 내 레코드 연결 구조 :
	- 그 노드별로는 양방향으로 되어있으나, 그 노드 안에서는 단뱡향으로 되어있다고 함. 
	- 그래서 그 노드 안에서 역방향으로 스캔을 해야해서 약간 비효율적이라고 함. 
- 2. 잠금 및 동시성 제어 : 
	- 페이지 잠금 메커니즘은 교착상태를 방지하기 위해서 정방향으로 주로 설계되어있다고 함.
	- 그래서 역방향은 조금 더 걸린다!
