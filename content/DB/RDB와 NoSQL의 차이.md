

### [[RDB]]와 [[NoSQL]]의 차이점??

- 데이터 모델 차이
	- RDB는 데이터를 테이블, 행, 열의 형태로 저장하는 구조화된 방식
	- NoSQL은 특정 모델이 아니라, 문서, 키-값, 그래프 등 다양한 형식으로 저장가능

- 스키마 차이
	- RDB는 데이터를 쓰기 전에 테이블 구조를 미리 정의해야함.
	- 이거를 쓰기 "쓰기 시 스키마" 라고 함. 
	- 데이터의 일관성과 무결성 높임. 근데 구조 변경이 복잡하다는 단점이 있다. 

	- NoSQL은 대부분 정해진 스키마가 없음.
	- 이런 방식을 "읽기 시 스키마" 라고 함. 
	- 변화하는 요구사항에 빠르게 대응할 수 있다는 장점이 있음. 

- 확장성 차이
	- RDB는 단일 서버의 성능(CPU, RAM)을 높이는 수직적 확장에 최적화 되어있다. 
	- 여러 서버로 부하를 분산하는 수평적 확장도 가능하지만 복잡한 기술과 아키텍처가 필요.

	- NoSQL은 설계 초기부터 수평적 확장을 생각하고 개발함. 
	- 여러대의 저렴한 서버를 클러스터로(비슷한 것들끼리) 묶어서 분산 저장함. 
	- 대규모 데이터를 효과적으로 처리하는데 용이함. 

- 일관성 모델 차이점 
	- RDB는 ACID 원칙을 철저히 준수. 
	- 강력한 일관성과 트랜잭션의 신뢰성을 보장.
	- 이는 금융거래같은 데이터 정확성이 중요한 시스템에 필수. 

	- NoSQL은 [[BASE 모델]]을 사용.
	- 엄격한 일관성을 완화하고 가용성과 분산환경에서 안정성을 우선시함. 
	- 여러 노드에 복제된 데이터는 시간이 지나면 결국 일관된 상태로 변한다는걸 최종적 일관성이라고 함. 
	> 단, MongoDB와 같은 최신 NoSQL 데이터 베이스는 ACID를 지원한다. 


### NoSQL 장점 및 단점 

- 강점 
	- 높은 확장성 
		- 수평적 확장이 용이
		- 서버를 추가하는 것으로 큰 데이터 볼륨과 높은 처리량을 감당할 수 있다. 
	- 스키마가 유연하다.
		- 정형, 반정형, 비정형 모두 쉽게 저장 가능. 
		- 요구사항 변화에 따라 데이터 모델을 신속하게 변경할 수 있다. 
		- 애자일(Agile) 개발환경에 매우 적합하다. 
	- 특정 워크로드에서 빠름
		- 복잡한 Join 연산을 피하고 데이터를 비정규화해서 저장하는 경우가 많음.
		- 특정 조회 패턴에 대해 매우 빠른 읽기/쓰기 성능과 낮은 지연시간을 제공. 
- 약점
	- 완벽한 일관성이 아님.
		- 최종적 일관성은 데이터의 변경 사항이 모든 노드에 즉시 반영되지 않을 수 있음. 
		- 금융거래 같은 엄격한 일관성이 요구되는 앱에서는 부적절. 
	- 표준이 없음. 
		- SQL같은 표준화된 쿼리 언어가 없어서 데이터베이스마다 사용하는 언어가 제각각
		- **MongoDB**는 JSON
		- Redis 는 `GET key`, `SET key value` 같은 간단한 명령어 등 언어가 다르다!
	- 복잡한 쿼리 처리가 힘듬
		- 데이터가 비정규화 되어있고, 여러 데이터 집합을 연결하는 복잡한 Join 연산이나 쿼리를 수행하기 힘듬

### RDB의 어떠한 특징 때문에 NoSQL에 비해 부하가 많이 걸릴 "수" 있을까요? (주의: 무조건 NoSQL이 RDB 보다 빠르다라고 생각하면 큰일 납니다!)

- Join 연산을 할떄 비용이 많이듬. 
	- RDB 설계의 핵심인 정규화는 데이터 중복을 최소화 하기 위해서 정보를 여러 테이블로 분리.
	- 이 분리된 데이터를 다시 합쳐서 조회 하려면 Join 연산이 필요한데 이게 비용이 높은 작업
	- NoSQL은 필요한 데이터를 하나의 문서나 행에 비정규화해서 저장. 
	- 그래서 단일 읽기 작업으로 조회를 끝내는 경우가 많아서 부하가 적음.

- ACID 준수하는 오버헤드
	- 일관성과 고립성을 지키려면, 복잡한 잠금(Locking) 메커니즘이 존재.
	- 트랜잭션 로그 기록 등 상당한 내부 오버헤드가 든다. 

- 엄격한 스키마 관리 비용
	- 스키마는 데이터 품질을 유지하지만, 변경하는 작업은 큰 부하를 유발한다. 
	- 대용량 테이블의 구조를 변경하는건 데이터를 재작성, 인덱스 재구성 등 서비스 중단까지 간다고 함.
	- 근데 유연한 스키마를 가진 NoSQL은 이런 운영상의 부하가 없다. 

- 수직적 확장의 한계
	- 수직적 확장 모델은 물리적, 비용적 한계가 있음. 


### RDB 대신 NoSQL을 선택하는 경우.

- 소셜 미디어 플랫폼에서 사용자 정보, 게시물 등을 보여줄때.
- 원래 RDB 를 사용하면 `Users`, `Posts`, `Followers`(연결 테이블), `Likes`(연결 테이블) 등으로 테이블을 설계 
- 그리고 이것들을 다 Join 해서 데이터를 가져와야함.
- 이럴 필요없이, NoSQL을 사용해서 그냥 게시물을 보여줄떄, 그곳에 필요한 정보들을 모두 때려박기!
- 정규화할 필요가 없으니까 분리도 안하고, join도 안하고! 아주 좋은데??


### 이렇게 정규화 안하고 좋으니까 빠른데 왜 NoSQL은 안써??

- 데이터 정합성 문제!
- 결국 동기화 되는 특징을 가지고있지만 시간이 좀 걸릴 수 있음. 


- **RDB (SQL)를 반드시 써야 하는 경우:**
    - **금융 거래, 결제 시스템, 재고 관리** 등 데이터의 정확성과 일관성이 1초라도 틀어지면 안 되는 경우  
    - 데이터 구조가 명확하고, 여러 데이터를 복잡하게 연결(JOIN)해서 분석해야 하는 경우  

- **NoSQL을 쓰는 것이 유리한 경우:**
    
    - **소셜 미디어 피드, 채팅, IoT 센서 데이터**처럼 데이터의 양이 엄청나고 실시간으로 빠르게 쓰고 읽어야 하는 경우  
    - 서비스가 절대 중단되면 안 되고(고가용성), 사용자가 늘어남에 따라 서버를 계속해서 쉽게 추가해야 하는(수평적 확장) 경우  
    - 데이터의 형식이 정해져 있지 않거나 자주 바뀌는 경우 (예: 사용자 프로필에 새로운 항목이 계속 추가될 때)
