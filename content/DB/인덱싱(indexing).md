

### 인덱스가 뭐야?? 

- 데이터베이스 인덱스는 테이블 전체를 스캔('Full Table Scan')하지 않고 빠르게 찾도록 도와주는 구조. 
- 가장 일반적으로는 B-Tree를 사용한다
- 책 맨뒤에 있는 찾아보기(목차)와 같다. 
	- 특정 주제를 찾아내기위해 책을 전체 읽는게 아니라 목차만 읽어서 빠르게 찾는것. 
- 인덱스는 읽기 쿼리일때 가장 강점이 나타남. 


### 어떤 컬럼에 생성해야할까??

- 데이터 필터링을 위한 Where 절에 해야함. 
- 테이블간 연결을 위한 Join 연산에 생성 (주로 외래키 컬럼에 생성)
- 데이터 정렬 및 그룹화를 위한 Order by, Group by 절에 있는 컬럼. 
- UNIQUE 또는 Primary Key 제약 조건이 있는 컬럼!

### 왜 빈번한 수정이 인덱싱을 방해할까??

- 인덱스는 읽기(SELECT)는 속도를 높이지만, 쓰기(INSERT, UPDATE, DELETE)는 속도를 늦춘다.
- 쓰기 작업이 느려지는 이유??
	- 데이터가 수정되면 해당 테이블에 생성된 모든 인덱스 또한 변경 사항을 반영해야해서 작업이 생긴다. 
- 과도한 인덱싱의 문제가 생길 수 있음. 
	- 하나의 테이블에 특히 쓰기 작업이 많은 테이블에 많은 인덱스를 생성하면 오히려 성능이 심각하게 저하될 수 있다. 
	- 인덱스는 정말 빈번하고, 중요한 쿼리에 명확하게 이점이 있을때만 생성해야한다. 

### 인덱스가 없을때, 쿼리는 어떻게 처리해? 

- 풀 테이블 스캔(Full Table Scan) 으로 처리한다. 
- 만약 쿼리에 where절에 인덱스 없는 컬럼이 조건으로 사용되면 전체를 다 뒤져봐야함. 
- 처음부터 마지막까지 모든 행을 읽으면서 쿼리 조건과 일치하는지 일일이 확인함. 
- 매우 비효율적이고 느리다, 그리고 테이블 전체를 디스크에서 메모리로 읽어와야해서 대량의 입출력 작업이 생긴다. 

- 풀 테이블 스캔이 허용되는 경우? 
	- 테이블 크기가 작아서 인덱스로 관리하면서 탐색하는것보다 모든 행을 스캔하는게 더 빠른경우. 
	- 쿼리가 테이블 대부분의 행을 반환해야하는 경우!
	- 인덱스를 통해 여러번 작업을 하는 것 보다 그냥 순차적으로 한번에 읽는것이 효율적일 수 있음. 


### ORDER BY/GROUP BY는 인덱스에 어떻게 영향이 있을까? 

- 인덱스가 없는 상태에서 Order by 나 Group by 연산을 하는건 비용이 많이듬. 
- DB는 먼저 조건에 맞는 모든 행을 가져온다. 
- 그리고 메모리나 디스크를 사용해서 명시적인 정렬 작업을 수행해야한다고 함. 이 정렬과정이 매우 오래걸릴 수 있음.

- 이 정렬과정을 도와주는데 인덱스!!!
	- B-Tree 같은 인덱스는 데이터를 이미 정렬된 상태로 유지하고있다. 
	- DB는 이 인덱스를 사용해서 별도의 정렬 단계 없이 이미 정렬된 순서로 데이터를 가져옴.

- 인덱스 사용을 위한 조건 
	- Order by 또는 Group by 절에 사용된 컬럼들이 인덱스를 사용하고싶다면 인덱스 컬럼과 일치해야함
	- 근데 여기서 왼쪽 접두사 규칙을 따르는데 이게 뭐냐면
		- (A, B) 컬럼에 대한 복합 인덱스가 있다면 order by A || order by A, B 는 인덱스를 타고 간다. 
		- 하지만 order by B 는 없다! 
	- 정렬 방향 (ASC, DESC) 또한 인덱스의 정렬 방향과 일치하거나, DB가 인덱스를 역순으로 스캔할 수 있어야 한다. 

### MySQL의 GroupBy 최적화는 조금 다르다

- MySQL에서 GroupBy는 두 가지 중 하나로 동작한다. 

- 인덱스를 사용하지 못할때 임시 테이블을 활용하는 방법
	- 인덱스를 활용하지 못하는 경우에는 데이터를 모두 읽어서 임시 테이블에 저장한 다음에 정렬 및 그룹화를 수행한다. 
	- CPU, I/O 비용이 크다. 
- 인덱스를 사용할 수 있을때
	- 인덱스를 순차적으로 읽으면서 그룹 경계가 바뀔 때마다 그룹을 결정한다
	- 임시 테이블이 필요없고 바로 집계가 가능함. 


##### 인덱스를 사용할 수 있을때 2가지 형태가 있음.

- 느슨한 인덱스 스캔(Loose Index Scan)
	- 인덱스 일부 키 값만 대표로 읽는 방식. 
	- 각 그룹별로 첫 번째 인덱스 엔트리만 읽고 나머지는 건너뛴다. 
	- 그러니까 대표노드만 보고 다음 그룹으로 넘어가는것.
	- 그래서 MIN, MAX 같은 집계함수는 사용할 수 있으나, SUM, AVG 같은 전체를 다 봐야하는건 이 느슨한 인덱스 스캔을 할 수 없음. 
![](https://i.imgur.com/nmV5gZa.png)

- 타이트한 인덱스 스캔(Tight Index Scan)
	- 인덱스 순서를 직접 따라가며 그룹이 바뀌는 지점을 탐지하는 방식.
	- 느슨한 인덱스 스캔보다는 느리지만 Count, SUM 이런 집계함수까지 다 가능. 
![](https://i.imgur.com/WLtD1OL.png)


### 기본키와 인덱스의 관계는 어떻게될까??

- 기본키는 인덱스인가?? 
	- 사실상 맞다. 
	- DBMS는 기본키 컬럼에 대해 고유 인덱스를 자동으로 생성한다.
- 기본키와 인덱스의 차이점
	- 목적의 차이
		- 기본키는 행을 고유하게 식별하는 것에 목적이있으나 
		- 인덱스는 쿼리 성능을 올리기 위해 하는 작업. 
- 클러스터형 인덱스와의 관계
	- SQL Server나 MySQL(InnoDB)와 같은 많은 시스템에서 기본키 인덱스는 기본적으로 [[클러스터형 인덱스]]가 된다. 
	- 기본키 순서대로 테이블의 데이터가 물리적으로 저장되기 때문에 기본키를 통한 조회가 매우 빠른것. 


### 외래키와 인덱스와의 관계는?? 

- 외래키는 자동으로 인덱싱 되나?? 
	- 이는 DBMS마다 다르다고 한다. 
	- PostgreSQL와 같은 인기있는 시스템에서는 외래키가 자동으로 인덱싱되지 않는다. 
	- 하지만 MySQL/MariaDB는 외래키에 대해 인덱스를 자동으로 생성한다. 

- 외래키를 (거의)항상 인덱싱 해야하는 이유는??
	- Join 성능을 높이기 위해
		- 외래키는 항상 Join 연산에 사용된다.
		- 만약 외래키에 인덱스가 없다면 자식테이블 전체를 스캔해야한다. 
	- 참조 무결성 유지보수 
		- 부모 테이블의 행이 DELETE 되거나, 기본키가 Update될때, DB는 자식테이블에 참조하고있는 행이 있는지 확인함. 
		- 이때 인덱스가 있으면 작업을 빨리 할 수 있는데, 없으면 전체를 스캔해야해서 느림.

### 인덱스가 데이터의 물리적 저장에도 영향을 미치나요? 그렇지 않다면, 데이터는 어떤 순서로 물리적으로 저장되나요?

###### [[클러스터형 인덱스]]와 비클러스터형 인덱스

- 두 인덱스 유형의 핵심 차이는 데이터가 디스크에 물리적으로 어떻게 저장되는지임. 

|**특성**|**클러스터형 인덱스 (Clustered Index)**|**비클러스터형 인덱스 (Non-Clustered Index)**|
|---|---|---|
|**물리적 데이터 순서**|인덱스 키의 순서에 따라 테이블 데이터의 물리적 순서를 결정함 110|데이터의 물리적 순서에 영향을 주지 않음. 인덱스의 논리적 순서와 데이터의 물리적 순서는 별개임 104|
|**테이블당 개수**|테이블당 하나만 존재 가능 109|테이블당 여러 개 존재 가능 104|
|**리프 노드 내용**|인덱스의 리프 노드가 곧 실제 데이터 페이지임 104|리프 노드는 인덱스 키 값과 실제 데이터 행을 가리키는 포인터(Row Locator)를 포함함 111|
|**저장 공간**|추가적인 저장 공간이 거의 필요 없음 (데이터 자체가 인덱스) 109|인덱스 구조를 위해 별도의 저장 공간이 필요함 104|
|**조회 성능**|매우 빠름 (특히 범위 검색). 추가적인 조회 단계가 없음 104|약간 느림. 인덱스에서 포인터를 찾은 후, 실제 데이터 행을 한 번 더 찾아가야 함 112|


### 우리가 아는 RDB가 아닌 NoSQL (ex. Redis, MongoDB 등)는 인덱스를 갖고 있나요? 만약 있다면, RDB의 인덱스와는 어떤 차이가 있을까요?'


- NoSQL 데이터베이스도 인덱스를 사용한다!
	- RDB에서와 마찬가지로 인덱스는 매우 중요하다. 

- RDB의 인덱스와의 차이점 
	- 데이터 구조 
		- 많은 NoSQL 데이터베이스도 B-Tree를 사용한다. (MongoDB)
		- 인덱싱되는 데이터의 성격이 다르다. 
		- NoSQL 데이터베이스는 문서 내의 중첩된 필드나, 배열 내의 요소에 대해서도 인덱스를 생성할 수 있다. 
	- 인덱스 유형 
		- NoSQL 데이터베이스는 자신들의 데이터 모델에 특화된 인덱스를 만들어서 사용 

|구분|MongoDB|Redis|
|---|---|---|
|데이터 모델|문서형 (JSON)|키-값|
|기본 인덱스|자동 생성 (단일 필드, 복합, 텍스트 등)|키(Key) 자체|
|값 기반 검색|자동 지원 (`find({age:25})`)|불가능 (직접 구현 필요)|
|인덱스 관리|MongoDB 엔진이 자동|사용자가 직접 유지|
|시간 복잡도|O(log n) (B-Tree 기반)|키 조회 O(1), 값 검색 O(n)|
|대표 활용|복잡한 질의(DB)|캐시, 세션 저장, 실시간 순위|

> [!note] 정리
> ## 요약 정리
> - **MongoDB:**
>     
>     - SQL DB처럼 다양한 인덱스 구조를 자동으로 지원 (B-Tree, Text, Geo 등)
>     - 쿼리 최적화 자동 수행
>         
> - **Redis:**
>     
>     - 키(Key) 자체가 인덱스 역할 (O(1) 조회)
>     - 값 기반 검색을 하려면 사용자가 직접 “보조 인덱스”를 구현해야 함 (Sorted Set, Set 등 사용)
