
- 트래픽이 폭주할떄 시스템이 붕괴되는 주된 원인은 병목과 경합 입니다. 
- 이를 해소하기 위해서 트래픽을 분산시키고, 유입량을 제어하며 데이터 접근 속도를 높이는 전략 필요.


### 트래픽 진입점 제어 : [[로드밸런서]]

- 로드밸런서는 단순히 트래픽을 나누는 도구가 아니라 시스템의 가용성을 결정짓는 첫번째 관문이다. 
- 대규모 시스템에서는 L4, L7 로드밸런싱을 혼합하여 사용하며, 상황에 맞는 알고리즘 선택이 필수적이다. 

- Layer4( 전송계층 ) 로드밸런서  
	- IP 주소와 포트번호를 기반으로 패킷을 라우팅
	- 패킷의 내용을 들여다보지 않으므로 처리속도가 매우 빠르고 부하가 적다. 
	- TCP 연결을 그대로 백엔드 서버로 토스하는 역할을 해서 대규모 트래픽 1차관문으로 적합하다. 

- Layer 7 (애플리케이션 계층) 로드밸런서 
	- HTTP 헤더, URL, 쿠키 등을 분석해서 정교한 라우팅을 수행한다. 
	- L7 로드밸런서는 **요청 안에 있는 글자(URI, 헤더, 쿠키)**를 읽을 수 있음 그래서 요청을 자세히 보고 “너는 결제 서버로 가라”, “너는 검색 서버로 가라” 이런 식으로 **정교한 분배**가 가능함.

```
- `/api/payment` → 결제 서버
- `/api/search` → 검색 서버
```
> **내용(콘텐츠)**을 기준으로 나눠줘서 **콘텐츠 기반 라우팅**이라고 함.

- Layer 7 로드밸런서는 HTTPS 암호 해제를 대신 해주는 역할도 가능. 
	- 사용자와 서버 사이에서 오가는 HTTPS 는 암호화 되어있어서 암호를 먼저 풀어서 뒤에 있는 서버에게는 평문 트래픽으로 전달해서 서버의 암호화/복호화 부담을 줄여줄 수 있음. 

- 그러나 CPU 를 많이 사용해서 무거운 방식. 

> [!note] 정리
> 
> L7 로드밸런서는 CPU를 많이 사용하지만 정교한 라우팅 수행 가능. 그리고 암호화 복호화 과정을 서버 대신 수행해서 서버의 부하를 줄여줄 수 있다. L4 로드밸런서는 IP 주소와 포트번호로 패킷을 라우팅해주고 속도가 매우 빠르다. (뭐 안하고 바로 토스해주기)

### 트래픽을 줄이는 캐싱 전략

- DB 는 물리적인 I/O를 동반하므로 확장에는 한계가 있다. 
- 트래픽이 몰릴때 DB를 보호하기 위한 캐싱 전략은 필수적이다. 

- 캐시 읽기 전략 
	- Look-aside(Lazy Loading)
		- 애플리케이션이 캐시를 먼저 확인하고 없음녀 DB에서 조회 후 캐시에 적재.
		- 애플리케이션의 요청이 캐시에 없으면 직접 DB에 접근해서 가져오는것. 
	- Read-through
		- 애플리케이션의 요청이 캐시에 없으면 캐시가 DB에 가서 가져오는 것. 
		- 애플리케이션은 캐시만 바라보고, 캐시가 DB 조회를 대행한다. 
		- 데이터 모델이 단순할 때 유리하다. 

> 보통 Look-aside 가 실무에서 흔하게 사용된다. 
> 더 코드가 단순하고 컨트롤하기 쉽다고 함, 그리고 캐시가 죽어도 서비스가 죽지 않음. Read-through 방식은 캐시가 DB에서 가져오는거기때문에 문제가 생기면 서비스 종료


### Cache Stampede (캐시 스탬피드) 문제(Thundering Herd(떼몰림) 문제라고도 함)

- 대규모 트래픽 환경에서 가장 빈번하게 발생하는 재앙적인 시나리오 
- 인기 있는 데이터의 캐시 만료 시점에 수천 개의 요청이 동시에 들어오면 모든 요청이 동시에 캐시 없음을 확인하고 DB에 쇄도.
- 이는 DB CPU를 100%로 만들고 서비스 전체를 다운시킬 수 있다. 
	- 확률적 조기 만료 
		- 캐시 만료 시간을 정확히 지키는 대신, 만료 시간 근처에서 확률적으로 미리 재갱신을 수행한다. 
		- TTL 이 60초라면 55초 ~ 60초 사이에 들어온 요청중 하나가 10%의 하나로 백그라운드에서 캐시를 갱신하도록 한다. 
	- 뮤텍스 락 (Mutex Lock)
		- 캐시 미스 발생 시, 즉시 DB로 가지 않고 분산 락을 획득하려 시도한다. 
		- 락을 획득한 단 하나의 요청만이 DB를 조회하여 캐시를 갱신하고, 나머지 요청은 잠시 대기하다가 갱신된 캐시를 읽는다. 


### DB 복제 아키텍처와 한계점 


#### Master-Slave 구조 
![](https://i.imgur.com/ea7nKfX.png)
- 가장 보편적인 구조로, 쓰기(Write)는 Master 노드에서만 처리하고 읽기(Read)는 다수의 Slave 노드로 분산한다. 
- 장점 
	- 쓰기 작업을 Master에서만 하니까 충돌 해결, 데이터 일관성 관리하는데 쉽다. 
- 단점 - 복제 지연 
	- Master에서 Slave 로 데이터가 넘어가는 과정은 보통 비동기 과정으로 처리된다.
	- 사용자가 데이터를 수정하고 조회할때 아직 업데이트 되지 않은 Slave 에서 데이터를 읽어서 방금 수정한 내용이 보이지 않는 정합성 문제가 발생한다. 
- 해결책 
	- Sticky Session 
		- 특정 사용자의 요청을 항상 Master 또는 특정 Slave 로 고정하면서 라우팅하는것. 
	- Version Check
		- 사용자가 마지막으로 쓴 타임 스탬프를 쿠키에 저장. 
		- Slave 에서 조회할때 해당 타임스탬프보다 최신 데이터가 있는 경우에만 읽도록 하거나 Master로 리다이렉트 한다. 

#### Active-Active (Multi-Master) 구조 

- 여러 데이터 센터에 각각 Master를 두어 쓰기 작업을 분산하고, 서로 데이터를 동기화 하는 구조. 
- 글로벌 서비스에서 지연 시간을 줄이고 가용성을 극대화 하기 위해 사용한다. 
- 두곳에서 모두 쓰기가 가능하므로 가용성이 매우 좋다. 하나가 장애가 발생했을 시 무중단으로 나머지 하나가 있으므로 서비스 가능하다는 장점이 있음. 
- 그러나 쓰기 충돌이 일어날 수 있다. (데이터 일관성 문제) 

###### 충돌을 어떻게 해결할까??

- Last-Write-Wins (LWW) 
	- 가장 단순한 방식 
	- 각 업데이트에 타임스탬프를 부여하고 가장 늦은 시간의 업데이트를 최종 데이터로 채택한다. 
	- 문제점 
		- 분산 시스템에는 각 서버의 물리적 시계가 완벽하게 일치할 수 없음.
		- 미세한 시간 차이로 인해 생기는 데이터 유실 가능성이 있음. 
-  CRDT (Conflict-Free Replicated Data Types)
	- 수학적으로 증명된 구조를 사용해서 어떤 순서던 간에 결국 동일한 상태로 수렴하도록 보장한다. 
	- Redis Enterprise나 Riak 같은 DB에서 지원하며, 채팅 앱의 메시지 동기화나 공동 편집 도구에서 필수적으로 사용됩니다. 
	- LWW의 데이터 유실 문제를 근본적으로 해결할 수 있는 강력한 도구. 

> [!bug] 주의!!
> 
> ### CRDT / LWW
> **분산 데이터 병합(Conflict Resolution)”을 해결하는 기술**
> 
> ##### 이 기술들이 해결하려는 문제
> Active-Active 구조에서 서버가 여러 개 동시에 쓰기 작업을 하면?
> - 같은 키에 대해 서로 다른 값이 들어옴
> - 순서가 뒤죽박죽 도착함
> - 데이터 충돌 발생
> - 네트워크 지연으로 값이 뒤늦게 도착
>   이때, “서버 여러 개가 동시에 다른 값을 썼는데, 최종적으로 어떤 값이 정답인가?” 를 해결하는 것이 **CRDT / LWW**이다. 
즉, CRDT/LWW는 **“데이터 충돌 병합” 문제를 해결**하는 기술임!!
