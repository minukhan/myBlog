
### Key (기본키, 후보키, 슈퍼키 등등...) 에 대해 설명해 주세요.

![](https://i.imgur.com/qzrrseW.png)


슈퍼키 > 후보키 > 대체키 > 기본키 

- 슈퍼키 : 
	- 각 행을 고유하게 식별할 수 있는 하나 이상의 속정 집합
	- 그러니까 행을 딱 알 수 있으면 다 슈퍼키임. 
	- 근데 불필요하게 여러개 있을 수 있음. (주민번호 , 이름 , 전화번호 , 집주소 ) 
	- 이것들이 다 후보키인데 여기서 주민번호만 있으면됨! 그걸 만족하는게 후보키.
- 후보키 : 
	- 슈퍼키 중에서 유일성 만족하면 후보키!
	- 후보키는 유일, NULL 값을 포함할 수 없음. 
- 기본키 : 
	- 후보키 중에서 레코드를 고유하게 식별하기 위해 선택한 단 하나의 키!
- 대체키 :
	- 후보키 중에서 기본키로 선택되지 않은 나머지 키
	- 주민번호 선택했다면, 학번처럼 후보키 인것들을 모두 대체키. 
- 외래키 : 
	- 어떤 테이블의 속성이 다른 테입르의 기본키를 참조
	- 테이블 간의 관계를 설정하고 참조 무결성을 강제. 
- 복합키 : 
	- 두개 이상의 속성이 조합되어서 하나의 기본키를 형성한 경우!
	- 단일로는 유일성 없을떄 사용. 
- 고유키 : 
	- 얘는 행이 고유하게 하는걸 찾는게 아니라 열(속성)을 중복 없게끔 만드는것!!
	- 기본키는 테이블의 대표 식별자고, 애는 그냥 속성 중복 없게끔해야지, 할때 설정하는 것.


### 기본키 수정 가능해??

- 기술적으로 수정이 가능!
- 새로운 값이 테이블 내에서 유일성을 유지하고 NULL 이 아니여야한다. 


##### 근데 기본키 값을 수정하는건 강력하게 권장하지 않는다!!

- 외래키의 연쇄적 업데이트
	- 기본키가 수정되면 외래키로 참조하는 모든 자식 테이블의 값들도 수정되어야 함. 
	- 수십 개의 테이블에 걸쳐서 대규모 업데이트를 유발할 수 있음. 
- 인덱스 유지보수 비용 
	- 기본키를 수정하는건 인덱스를 수정하는걸 의미. 
	- 이는 훨씬 큰 비용이 든다. 
- 외부 시스템과의 종속성
	- 애플리케이션 캐시, 다른 데이터베이스, 로그파일, URL 일부로 사용되고 있다면 (연결되어있다면)
	- 데이터가 바뀌면서 연결이 끊기는 문제가 발생. 


- 보통 기본키 수정하는 경우는 시간이 지남에 따라서 변경될 가능성이 있는 데이터로 기본키를 했을때 발생한다. 

### MySQL 기본키 설정 안해도 만들어짐!! 왜그럼?? 

- MySQL의 [[InnoDB]]는 모든 테이블이 기본키를 가질걸 요구. 
- InnoDB가 [[클러스터형 인덱스]] 구조를 사용하기 때문.
	- 그래서 테이블의 데이터가 기본키 순서에 따라서 물리적으로 정렬되어 저장된다. 

> 만약 사용자가 명시적으로 기본키를 정의하지 않으면, InnoDB는 우선순위에 따라 기본키를 자동으로 선택하거나 생성한다. 

- 1. InnoDB는 테이블에 정의된 인덱스 중, 모든 컬럼이 NOT NULL로 정의된 첫 번째 UNIQUE 인덱스를 찾아서 기본키로 설정한다. 
- 2. 만약 적절한 UNIQUE 인덱스가 없다면 내부적으로 숨겨진 클러스텨형 인덱스를 생성.
	- `GEN_CLUST_INDEX` 또는 `ROW_ID`라고 불림
	- 새로운 행이 추가될 때마다 단조롭게 증가하는 값을 가짐. 
	- 이 키는 사용자에게 보이지 않으며, 직접 참조할 수 없음. 

- 이렇게 기본키 없어도 테이블 생성이 가능하지만 좋은 설계가 아님. 
- 데이터 모델에 맞는 의미있는 기본키를 정의해라!

### 외래키 컬럼에 NULL이 들어올 수 있나?? 

- 가능하다! 
- 해당 컬럼이 NOT NULL 제약조건으로 정의되지 않았을 경우 가능. 
- null 이라면 참조를 하지 않는다 라는 의미.
- 외래키에 NULL이 있다고 해서 참조 무결성을 위반하는건 아니다.
- 참조 무결성 제약은 외래키 값이 NULL이 아닌 경우에만 해당 값이 부모 테이블의 기본키에 반드시 존재해야 함을 요구함. 

### 어떤 칼럼의 정의에 UNIQUE 키워드가 붙는다고 가정해 봅시다. 이 칼럼을 활용한 쿼리의 성능은 그렇지 않은 것과 비교해서 어떻게 다를까요?

- 대부분의 DBMS에서  UNIQUE 제약 조건을 추가하면 해당 컬럼에 인덱스 생성!

- 장점 
	- 당연히 인덱스가 생성되니까 특정 값을 찾기 위해서 매우 효율적인 탐색을 함.(B-TREE 인덱스 탐색)을 수행. 
	- 옵티마이저가 고유함을 알기에, 일치하는 값을 찾으면 더이상 찾지 않아서 빠름. 
	- 옵티마이저가 더 나은 실행계획을 세운다.

- 단점 
	- DML 오버헤드
		- 주된 성능 비용은 INSERT, UPDATE 연산중에서 발생한다. 
		- 새로운 행이 추가되거나 기존 행이 수정될 때마다, 제약조건위반 여부를 확인하기 위해서 인덱스를 먼저 확인해야함.
		- 추가적인 오버헤드가 발생하게된다 인덱스때문에!
	- 인덱스 유지보수 비용이듬.
		- INSERT, UPDATE, DELETE 연산이 발생할 때마다, 인덱스 자체도 함께 업데이트 되어야함. 
		- 이떄 리소스를 소모하며 속도를 저하시킬 수 있음. 

- 참 이게 있으면 좋은점도 있고 단점도 있어서 잘 사용해야함.

> `WHERE` 절의 검색 조건으로 자주 사용되고 데이터 무결성을 위해서 유일성이 보장되는 경우에는 UNIQUE 제약조건을 사용하는게 바람직하다. 

> [!note] 정리
> 
> 제약조건은 규칙을 강제하는걸 넘어서 쿼리 옵티마이저에게 중요한 정보를 제공하는 역할도 함. 
> 이 컬럼이 고유하다라는 정보는 더 지능적이고, 빠른 실행 계획을 세울 수 있도록 많이 도와줌.
> 
> UNIQUE 를 걸면! -> 그 특정 컬럼의 INDEX를 생성한다.
