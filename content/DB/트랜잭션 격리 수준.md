
### 트랜잭션 격리 수준이란??

- 다중 사용자 시스템에서 여러 트랜잭션이 동시에 실행될 수 있다. 
- 격리 수준은 한 트랜잭션에 의해 만들어진 변경사항이 다른 트랜잭션에서 언제 적용할껀지!! 그거를 나눠놓은게 트랜잭션 격리수준


### 해결해야할 트랜잭션 동시성 문제

- 더티 리드(**(Dirty Read)**) :
	- 한 트랜잭션이 수정한 데이터를 다른 트랜잭션이 원본이 아니라 수정된걸 바로 읽어와버리는 현상. 
	- 이게 문제가 나중에 롤백되면 없는 값을 읽어버리게 된것. 
- 반복 불가능한 읽기 (Non-Repeatable Read) :
	- 한 트랜잭션에서 똑같은 명령어 2번 했는데 그 사이에 수정되어서 두개의 값이 다른경우. 
	- 여기서는 값이 변경된거를 조회하는것임! 행이추가되는게 아님. 
	- Update
- 팬텀 리드 (Phantom Read) :
	- 범위 쿼리를 2번 실행했을 때
	- 첫 번째 쿼리에서 없었던 행이 두 번째 쿼리에서 나타나는 현상
	- Insert, Delete

### 그래서 나온게 SQL-92 표준 4가지 격리수준 

| **격리 수준 (Isolation Level)** | **더티 리드 (Dirty Read)** | **반복 불가능한 읽기 (Non-Repeatable Read)** | **팬텀 리드 (Phantom Read)** |
| --------------------------- | ---------------------- | ------------------------------------ | ------------------------ |
| **Read Uncommitted**        | 발생 가능                  | 발생 가능                                | 발생 가능                    |
| **Read Committed**          | 방지                     | 발생 가능                                | 발생 가능                    |
| **Repeatable Read**         | 방지                     | 방지                                   | 발생 가능                    |
| **Serializable**            | 방지                     | 방지                                   | 방지                       |

### 모든 DBMS가 4개의 레벨을 모두 구현하고 있나요? 그렇지 않다면 그 이유는 무엇일까요?

- **MySQL (InnoDB):** 
	- 네 가지 표준 수준을 모두 구현
	- `Repeatable Read`는 다중 버전 동시성 제어(MVCC)와 갭 락(Gap Lock)이라는 메커니즘을 통해 대부분의 팬텀 리드 현상까지 방지
- **PostgreSQL** : 
	- `Read Committed`, `Repeatable Read`, `Serializable`을 구현
	- `Read Uncommitted` 수준은 내부적으로 `Read Committed`와 동일하게 동작
- **SQL Server** : 
	- 네 가지 표준 수준을 모두 구현
	- 낙관적 동시성 제어에 기반한 `Snapshot`과 `Read Committed Snapshot`이라는 두 가지 추가 수준을 제공


### 만약 MySQL을 사용하고 있다면, (InnoDB 기준) Undo 영역과 Redo 영역에 대해 설명

##### WAL (Write-Ahead Logging)

데이터 파일에 실제 변경을 쓰기 **전에**, 그 변경 내용을 **로그(redo log)** 에 **먼저 기록**하고 디스크에 **확실히 플러시**(fsync)하는 규칙

- Redo 로그 : 
	- 지속성 및 복구를 위해 존재.
	- 시스템 장애시 복구에 사용된다. 
	- WAL 원칙을 사용함. 변경사항은 실제 데이터 파일에 쓰이기 전에 Redo로그에 먼저 기록. 
	- 서버가 다운되면 InnoDB는 Redo로그를 재생.
- Undo 로그 :
	- 트랜잭션 롤백을 지원 
	- 트랜잭션이 롤백되면 Undo 로그의 이전 이미지를 사용해서 원래 상태로 복원 
	- MVCC :
		- `REPEATABLE READ` 또는 `READ COMMITTED` 수준에서 트랜잭션이 데이터를 읽을 때
		- 잠금을 거는게 아니라 Undo로그에 저장된 버전의 데이터를 읽도록 하는 것. (이전버전을 읽는것)
		- 그러면 읽기, 쓰기 작업을 차단하지 않아도 됨. 동시성 향상!!

>[!question] MVCC가 뭐야?? 
> ## **MVCC (Multi-Version Concurrency Control)**
> 데이터베이스에서 동시성을 제어하고 일관성을 유지하기 위한 기법
> - 데이터의 여러개의 버전을 보관해서 여러 트랜잭션이 동시에 처리할 수 있게끔 하는것.
> - MySQL의 Undo테이블이 여기에 속함.

**정상 커밋 경로**  
BEGIN → (Undo 기록) → (버퍼 수정=더티) → (Redo 기록) → COMMIT → (백그라운드 Flush/체크포인트) → 완료

## 쓰기 트랜잭션의 기본 흐름

1. **BEGIN**  
    트랜잭션 시작.
    
2. **변경 시도(UPDATE/INSERT/DELETE)**
    
    - **Undo 기록**: 바꾸기 전 값을 Undo 로그에 저장(되돌릴 준비).
    - **버퍼 변경**: 메모리(버퍼 풀) 페이지를 수정(더티 페이지가 됨).
		- 이렇게 **메모리 내용과 디스크 내용이 달라진 페이지**를 **더티 페이지**라고 함. 
		- **버퍼 풀(Buffer Pool)**은 **디비 서버 RAM(메모리)** 안에 있는 **InnoDB의 큰 캐시 공간**
    - **Redo 기록**: 바뀐 ‘내용/의도’를 Redo 로그에 **먼저** 적음(WAL).
        
3. **COMMIT**
    
    - 트랜잭션이 **확정**됨.
    - 잠금 해제.
    - 더티 페이지는 추후 **체크포인트** 때 디스크로 내려감(즉시 아닐 수 있음).
    - Undo는 **롤백용** 목적은 끝났지만, **MVCC 스냅샷**이 참조 중이면 잠깐 더 남아있을 수 있음(나중에 Purge가 청소).


**롤백 경로**  
BEGIN → (Undo 기록) → 문제 발생 → **Undo로 되돌림** → ROLLBACK → 완료
## ROLLBACK(되돌리기) 때

1. 트랜잭션이 문제로 **ROLLBACK** 요청됨.
2. 변경했던 레코드마다 **Undo 로그의 과거 값**을 읽어 **원상복구**.
3. 트랜잭션이 잡고 있던 잠금 해제.
4. Undo 레코드는 더 이상 필요 없으면 Purge가 정리.
    

> 한 줄 요약: **Undo = ROLLBACK 때 “이전 값”으로 되돌릴 안내서.**




**크래시 후 재시작**  
재부팅 → **Redo 재생**(page LSN < log LSN만 적용) → **미커밋 롤백**(Undo 사용) → 완료

## Crash 발생 후 재시작(크래시 복구) 때

1. 서버가 **갑자기 종료**됨(정전 등).
2. 재기동 시 **Redo 로그를 재생(redo)**
    - 각 페이지의 **page LSN**과 로그의 **log LSN**을 비교해서,
    - **page LSN < log LSN**이면 해당 로그를 **다시 적용**해 최신 상태로 맞춤.
3. **미커밋** 상태였던 트랜잭션은 자동으로 **롤백**(Undo 사용).
4. 일관된 시점으로 복구 완료.

**LSN(Log Sequence Number)** = **InnoDB 리두 로그 스트림에서 계속 증가하는 일련번호**

	- 동시성 제어 : 
		- 격리수준을 강제하기 위해 동시접근을 관리.
