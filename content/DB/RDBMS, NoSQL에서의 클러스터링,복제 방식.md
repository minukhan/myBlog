

### 클러스터링, 복제 환경??

- 클러스터링은 여러개의 서버를 하나의 시스템처럼 동작하도록 그룹화 시키는 기술. 
- 복제는 여러 서버에 데이터의 복사본을 유지하는 기술.
- 두 기술의 주된 목표는 고가용성!
	- 시스템 장애시에도 서비스를 중단없이 제공하는게 고가용성
- 사용자 증가에 따라서 시스템을 수평적으로 확장하는 수평 확장성


### RDBMS 접근방식

- 전통적인 관계형 DBMS는 단일 서버의 성능을 높이는 수직확장 방식으로 설계됨. 
	- 그래서 엄격한 ACID를 지킨다. 
	- 여러 서버로 확장하는 스케일 아웃 환경에서는 어려움에 직면한다. 
- 보통 이런 한계를 극복하기 위해서 마스터 - 슬레이브 복제 방식으로 부하를 분산하고 고가용성을 확보한다. 

- RDBMS 고가용성 솔루션의 대표적인 예 : MySQL InnoDB Cluster
	- 3가지 핵심 구성 요소로 되어있음.
	- MySQL Group Replication
		- 여러 대의 MySQL 서버가 한 팀(그룹)으로 묶여 같은 데이터를 **동시에 공유**하고, 한 대가 고장 나면 **자동으로 리더(Primary)를 갈아끼워** 서비스가 멈추지 않게 하는 고가용성 기능
	- MySQL Router
		- 쿼리 요청을 현재 정상적으로 작동하는 주 노드로 투명하게 라우팅 하는 역할
	- MySQL Shell
		- 클러스터의 구성, 관리, 모니터링을 돕는 도구

### NoSQL 접근방식

- 설계 초기부터 클라우드 환경, 수평확장을 염두에 두고 개발함. 
- 일관성과 가용성 사이의 트레이오프가 있다. 
- MongoDB의 레플리카 셋(Replica Set)
	- NoSQL의 복제 방식을 잘 보여주는 사례
	- 하나의 주(Primary) 노드가 모든 쓰기(Write) 연산을 처리하고, 이 연산 기록을 담은 오퍼레이션 로그(oplog)를 여러 개의 보조(Secondary) 노드들이 비동기적으로 복제
	- 장애가 발생하면 보조 노드를 선출해서 갈아끼우는 방식

- 그래서 RDBMS 와 NoSQL의 복제 방식 차이는 RDBMS는 강력한 일관성을 유지하려고 노력함. 
- 그러나 NoSQL은 일시적인 데이터 불일치를 감수하고 가용성을 확대하는 방향을 선택한다! 


### 분산 시스템에서의 트랜잭션 관리 

- 여러 독립적인 서비스나 DB에 걸쳐있는 작업을 원자적으로 처리하는건 매우 어려움. 
- 원자성을 어떻게 보장할 것인가?? 가 핵심 문제. 


#### 2단계 커밋 (Two-Phase Commit, 2PC)

- 분산 트랜잭션의 모든 참여자가 전부 커밋하거나, 롤백하도록 보장하는 동기식 프로토콜 
- 2단계로 이루어진다고 한다. 

	- 1. 준비단계
		- 트랜잭션 코디네이터가 모든 참여자에게 트랜잭션을 커밋할 준비가 되었는지 물어봄. 
		- 각 참여자는 작업을 완료할 수 있으면 준비완료를, 아니면 거부를 응답. 
	- 2. 커밋 단계
		- 모든 참여자들에게 준비 완료 응답을 받으면 모든 참여자에게 커밋명령을 내린다. 
		- 한명이라도 거부를 응답하면 모든 참여자에게 롤백 명령을 내린다. 
- 가장 큰 장점은 매우 강력한 일관성! 
- 모든 참여자의 응답을 기다리는 동안 모든 리소스가 잠금상태가 되는 블로킹 이 문제.
- 코디네이터가 실패하면 전체 시스템이 멈출 수 있는 단일 장애점이 될 수 있다. 
- MSA 구조에서는 부적합하다. 
![](https://i.imgur.com/EFnTw1w.png)


##### 사가 패턴 (The Saga Pattern)

- **여러 개의 “로컬 트랜잭션”이 각 서비스에서 독립적으로 커밋**되고, 
- 단계 사이를 **이벤트/명령으로 느슨하게 연결**하는 방식

- 일련의 로컬 트랜잭션을 순차적으로 실행.
- 분산 트랜잭션을 관리하는 비동기식 패턴 
- 각 로컬 트랜잭션이 성공적으로 완료되면, 다음 로컬 트랜잭션을 실행하도록 이벤트를 발생시킨다. 
- 만약 어느 단계에서든 트랜잭션이 실패하면, 성공했던 단계를 되돌리는 보상 트랜잭션을 역순으로 실행해서 전체 작업 취소한다. 
- 중앙 코디네이터 없이 각 서비스가 이벤트를 구동하고 발행하는 방식임. 

- 사가 패턴은 개별 서비스의 독립성을 보장하고 시스템 가용성, 회복 탄력성 높임. 
- 근데 트랜잭션이 실행되는 중간에 데이터 불일치 문제가 발생할 수 있음. 
	- 왜?
		- **읽는 시점이 제각각**  
		- 비동기 지연/ 재시도 발생 등등 
- 그래서 생기는게 더티 리드. 
- 분실 업데이트


##### 사가 패턴에는 2가지 종류가 있다. 

- Choreography 방식
	- 게시 - 구독 원칙을 적용하여 SAGA를 조정하는 기능
	- 구성을 통해 각마이크로 서비스는 자체 로컬 트랜잭션을 실행
	- 이벤트를 메시지 브로커 시스템에 게시하고 다른 서비스에서 로컬 트랜잭션을 트리거함. 
	- 보통 많은 서비스 트랜잭션 단계가 필요하지 않은 간단한 플로우에 적합. 
![](https://i.imgur.com/rJ5Kudx.png)


- **Orchestration 방식**
	- 중앙 집중식 컨트롤러 마이크로 서비스 
	- SAGA 트랜잭션을 실행하고 중앙 집중식으로 관리하며 단계 중 하나가 실패하면 보상 트랜잭션으로 롤백 단계를 실행. 
	- 많은 단계를 포함하는 복잡한 플로우에 적합.

### 마스터, 슬레이브 데이터 동기화 전 까지의 데이터 정합성을 지키는 방법??


- 비동기 마스터 - 슬레이브 복제 환경에서는 마스터에서 발생한 쓰기작업이 슬레이브에 적용되기까지 무조껀 지연시간이 발생한다. 
- 이를 복제 지연이라고 함. 

- 이러한 지연은 방금 저장한게 안보이는 불일치 현상을 유발할 수 있다. 
- 복제 지연은 가용성과 성능을 위해서 일관성을 희상한 느낌. 


- 정합성를 유지하기 위한 전략 

##### 마스터에서 읽기

- 사용자가 자신의 프로필을 수정하는 과정같은 강력한 일관성이 필요하다면 슬레이브가 아니라 마스터로 직접 요청을 보낸다. 
- 이는 정합성을 보장하지만 마스터의 부하가 증가. 분산하려고 슬레이브 둔건데 분산이 안됨. 

##### 동기식 복제 

- 마스터가 쓰기 작업을 완료하기 전에 최소 하나 이상의 슬레이브로부터 변경사항이 적용됐다는 확인을 기다리는 방식 
- 동기화는 좋으나, 지연시간이 생긴다. 

##### 지능형 프록시 계층

- 애플리케이션과 DB 사이에 위치한 프록시가 각 슬레이브의 복제 상태를 추적.
- 최신 데이터를 가진 슬레이브로만 읽기 요청을 라우팅. 

##### 애플리케이션 레벨 로직

- 쓰기 작업 후 반환된 트랜잭션 식별자를 기억
- 해당 식별자까지 복제가 완료된 슬레이브에게만 쿼리를 보내도록 구현. 

##### 복제 성능 튜닝

- 복제 지연의 근본 원인을 해결하는 방법. 
- 슬레이브에서 병렬 복제를 활성화시켜서 여러 스레드가 동시에 변경사항을 적용하게 함.
- 빠르게 적용시켜서 최적화


### 동시 트랜잭션에서 교착상태


- 교착상태는 두개 이상의 트랜잭션이 무한히 공유 자원을 기다리는 현상.

- 교착상태 발생 4가지 필요조건
	- 상호 배제 
	- 점유 및 대기
	- 비선점
	- 순환대기

- 보통 교착상태를 처리하기 위해서 3가지 전략이 있다. 

- 1. 예방 
	- 그냥 교착상태를 일어나지 않도록 하는 것
	- 락, 제한을 두어서 순서를 정해줌.
	- 구현이 복잡, 동시성이 떨어짐. 

- 2. 회피
	- 자원할당이 들어오면 이거 할당해주면 시스템 괜찮나? 다른것들 다 고려해서 판단
	- 은행원 알고리즘 
	- 모든 프로세스의 최대 자원 요구량을 알아야해서 너무 힘듬.

- 3. 탐지 및 회복 
	- 가장 현실적이고 많이 사용하는 방법 
	- 교착상태 일어날꺼면 일어나라, 근데 이거 일어났을때 탐지해서 회복시키겠다. 

- 탐지 및 회복을 사용하는 이유는 물론 다 예방하고 회피하면 좋겠지만 너무 오버헤드가 크다. 
- 그래서 현실과 타협해서 동시성도 허용하고, 교착상태는 드물게 발생하기때문에 유연성과 성능을 챙겼다.  


### 샤딩 방식은 무엇인가요? 만약 본인이 DB를 분산해서 관리해야 한다면, 레플리케이션 방식과 샤딩 방식 중 어떤 것을 사용할 것 같나요?


![](https://i.imgur.com/HJcRRhY.png)

##### 샤딩이란??

- 거대한 DB를 샤드(shard)라고 불리는 더 작은 단위로 분할해서 여러 서버에 분산저장.
- 수평확장 아키텍처 패턴 
- 복제는 데이터를 복사하지만 샤딩은 진짜 분할시켜버린다. 

##### 샤딩 전략??

- 데이터를 어떤 샤드에 저장할지 결정하는 기준이 되는 컬럼을 샤드 키(Shard Key) 라고 한다. 
- 이를 어떻게 정의하느냐에 따라서 여러 전략으로 나뉜다. 

- 1. 범위 기반 샤딩 
	- 샤드 키 값 범위를 기준으로 데이터를 분할. 
	- 구현이 쉽지만 특정 범위에 몰릴경우 핫스팟(hotpot)이 발생해서 특정 샤드만 힘들어짐. 

- 2. 해시 기반 샤딩 
	- 샤드 키값을 해시함수에 입력
	- 그 결과값에 따라 데이터를 분산 
	- 모든 샤드에 비교적 균등하게 분배되어 핫스팟을 방지. 
	- 연속적인 키값이 서로 다른 샤드에 흩어져서 범위 기반 쿼리는 오히려 성능이 안좋음. 

- 3. 디렉터리 기반 샤딩 
	- 어떤 키가 어떤 샤드에 저장되어있는지 매핑하는 테이블을 관리. 
	- 이 테이블 자체가 성능 병목이나 단일 장애점이 될 수 있다. 

- 쓰기 요청이 들어오면 여러 샤드로 분산되어 처리하므로 병렬처리가 가능해져서 빠름. 


### 어떨때 샤딩을 써야하고 어떨때 복제를 사용해야하나??

- 복제를 사용하는 경우
	- 주된 요청이 읽기인경우.
	- 고가용성, 재해 복구가 핵심 요구사항일때 선택
	- 복제는 샤딩에 비해 구현 및 관리가 쉬움. 

- 샤딩을 사용하는 경우 
	- 주로 요청이 쓰기인경우
	- 전체 데이터 셋의 크기가 단일 서버의 용량을 초과할때.
	- 여러 서버로 분산해서 단일 머신의 한계를 극복. 
	- 그러나 올바른 샤드로 라우팅하는 구현 복잡도가 높아짐. 


- 하이브리드 전략도 있다고 함. (샤딩된 복제본)
	- 읽기 트래픽이 증가하면 읽기 전용 복제본, 만약 쓰기 트래픽이 증가하면 쓰기 부하를 분산시키기 위한 샤딩을 도입. 
	- 샤드의 안정성을 높이기 위해서 샤드별로 복제를 구성.
