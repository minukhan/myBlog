
### 캐싱이란?? 

- DB에 접근하기 전에 캐시되어있는 곳을 살펴보고 있으면 그곳의 데이터를 사용하여 효율을 챙기는 방법 


### 동작 과정 

- 요청 발생
	- 클라이언트가 데이터를 요청하면 DB가 아니라 캐시를 먼저 조회. 
- 캐시 히트(Cache Hit)
	- 만약 캐시에 존재한다면 캐시에서 즉시 반환한다(이게 빨라서 사용하는 것)
- 캐시 미스(Cache Miss)
	- 만약 데이터가 캐시에 없으면 DB에서 조회한다. 
	- 조회된 데이터를 캐시에 저장한 후 클라이언트에게 반환한다. 

### 특징

- 캐시가 장애가 생겨도 DB에서 조회할 수 있으므로 서비스 중단 위험은 없다. 
- 그러나 초기에는 다 미스라서 DB 부하가 증가한다. (안쓰는거보다 느리겠지)
- 만약 캐시의 갱신이 지연되면 실제 DB의 데이터와 불일치 문제가 생길 수 있음. 
	- DB 값이 수정되었지만, 캐시에 기존 데이터가 남아 있는 경우
	- 캐시가 오래되어 최신 상태를 반영하지 못하는 경우

### 캐시 불일치 문제를 방지하기 위해서 쓰기 전략이 있다. 

- Write Through(동시 쓰기 방식)
	- DB와 캐시를 동시에 업데이트 하는 방식
		- 만약 애플리케이션이 데이터를 변경을 요청하면
		- 캐시를 먼저 업데이트한다. 
		- 그리고 캐시 시스템이 DB에 동기적으로 반영시킴. 
	- 항상 최신 상태를 유지한다. 
	- 모든 쓰기 요청이 2번 발생하게 됨(DB + Cache)
	- 자주 변경되는 데이터는 리소스 낭비가 될 수 있다. 
	- TTL을 설정해서 불필요한 데이터는 자동으로 만료되게끔 하는게 좋다. 
![](https://i.imgur.com/gV2B1Jh.png)

- Cache Invalidation(무효화 방식 / 캐시 삭제 방식)
	-  DB 변경시 캐시를 삭제하는 방법 
		- DB데이터를 먼저 변경.
		- 그리고 해당하는 캐시의 데이터를 삭제한다.
		- 이후에 조회할때, 다시 DB에서 읽고 캐시에 갱신한다. 
	- 캐시 불일치 걱정이 없다. 
	- Write Through 방식보다 더 효율적이다. 
![](https://i.imgur.com/kPx1kwT.png)

- Write Behind (Write Back) (지연 쓰기 방식 / 후행 쓰기 방식)
	- 캐시를 먼저 업데이트하고 일정시간 뒤에 비동기적으로 DB에 반영
		- 쓰기 요청이 들어오면 캐시만 업데이트.
		- 일정시간, 조건에 따라 DB에 비동기 반영한다. 
	- DB 부하가 줄고, 성능이 개선.
	- 대량의 쓰기작업을 배치로 처리 가능하다 .
	-  DB와 캐시가 일시적으로 불일치 할 수 있다. 
	- 캐시서버가 장애시, 아직 반영되지 않은 데이터가 날라갈 수 있음.
