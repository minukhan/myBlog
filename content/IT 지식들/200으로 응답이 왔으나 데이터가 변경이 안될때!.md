

- Datadog, New Relic, AWS CloudWatch와 같은 인프라 모니터링 도구와 로드 밸런서는 서비스의 건강 상태를 판단할때 HTTP 상태 코드를 1차적인 지표로 삼는다. 
- 만약 200이 반환되었다면 에러율에 포착되지 않아서 장애가 발생했음에도 대응 시간을 지연시킨다. 

### 그래서 생기는 문제가 뭐야? 

- 캐싱의 오작동
	- CDN 이나 브라우저는 기본적으로 200 OK 응답을 캐싱 가능한 것으로 간주한다. 
	- 만약 재고 없음이라는 에러 메시지가 200 OK로 반환되어 캐싱 된다면 계속 에러메시지를 보게 될 것이다. 

- API 요청이 서버에 도달했으나 비즈니스 규칙이나 데이터 상태로 인해 요청을 처리할 수 없는 경우에는 상황에 맞는 구체적인 4xx 상태코드를 사용 해야함. 
- “200만 쓰지 말고 상황에 맞는 상태코드를 사용하라”

##### 2.1 **문법 오류 → 400 Bad Request**

- JSON 파싱 오류
- 필수 필드 누락
 **사용자 데이터 형식 자체가 잘못됨**
 
##### 2.2 **비즈니스 규칙 실패 → 422 Unprocessable Entity**

요청 문법은 정상이지만 **비즈니스 로직에 어긋나는 경우**

- 금액 > 잔액
- 비밀번호 복잡도 불충족
- 음수 나이 입력

**클라이언트가 데이터 의미론을 잘못 사용한 오류**

##### 2.3 **리소스 상태 충돌 → 409 Conflict**

- 중복 이메일 회원가입
- Optimistic Lock 버전 충돌
    

 **리소스 상태 때문에 요청을 처리할 수 없음**

##### 2.4 **데이터 변동 없음(멱등) → 200 또는 204**

- 프로필 수정 요청을 보냈는데 실제 데이터가 기존과 동일한 경우

정상 처리임 → **에러 아님!**
