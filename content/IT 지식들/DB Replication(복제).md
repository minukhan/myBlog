

### DB Replication란??

- 모든 DB서버가 똑같은 데이터를 가짐.
- 실시간으로 똑같아 지도록 동기화과정이 필요
- 서버의 역할을 분리하는 용도로 사용

### DB Replication 하는 이유가 뭐야??

- 부하분산
	- 애플리케이션에서 DB 트래픽은 보통 READ임
	- 쓰기(INSERT, UPDATE, DELETE) 작업은 **Source (Primary)** DB에서만 처리
	- 모든 읽기 작업은 다수의 Replica DB로 분산시킨다. 
	- **Source DB는 쓰기 작업에만 집중할 수 있게 되어 전체 시스템의 성능과 처리량이 극대화 된다고 한다. 

- 고가용성 및 장애 조치
	- 만약 **Source DB에 장애가 발생해도 서비스 중단을 최소화할 수 있다. 
	- 만약 문제가 생기면 Replica DB중 하나를 즉시 새로운 Source DB로 만들어버림. 
	- 그래서 서비스는 거의 중단없이 바로 재개 가능. 

- 데이터 분석 및 리포팅
	- 운영 DB에서 무거운 분석용 쿼리를 실행하면 실제 서비스 성능이 너무 느려짐. 
	- 그래서 Replica DB에서 수행하며 서비스에 문제 생기지 않도록 함. 

- 안전하게 백업 가능
	- Source DB를 직접 백업하면, 백업하는동안 테이블에 Lock이 걸려서 서비스 중단. 
	- 복제된 DB를 사용하면 그런거 없이 백업본 확보 가능.

### 복제된 DB들 동기화하는 방식 종류 3가지 

- 비동기 복제 (기본)
	- Source DB는 트랜잭션을 커밋한 후 Replica가 데이터를 받아갔는지 신경쓰지 않고 클라이언트에게 성공 응답. 
	- 그냥 남일임. 복제일은. 
	- 이러면 성능 저하가 없어서 좋음. 
	- 그러나 만약 커밋 이후에 바로 장애가 발생하면 데이터가 Replica로 전송 안될 수 있어서 데이터 유실이 발생한다. 

- 준동기 복제
	- Source DB가 트랜잭션을 커밋한 후 최소 1개의 Replica가 Relay Log에 이 내용이 저장됐는지 확인 한 후에 클라이언트에게 응답. 
		- Log에 기록하는것만 확인하는거지, Replica에 데이터를 적용시키기까지 기다리는건 아님. 
	- 비동기 방식보다 훨씬 안정성이 높음. 
	- Source DB가 장애시, 최소 1개의 Replica는 존재함. 
	- 그러나 그만큼 지연된다. 

- 동기 복제 
	- Source DB가 트랜잭션을 커밋하고 모든 Replica가 데이터를 적용할때까지 기다린다. 
	- MySQL 기본 Replication 기능에는 지원하지 않음.
	- 데이터 정합성이 완벽하게 보장된다.
	- 너무 느림. 
	- 하나의 Replica에 문제생기면 전체 쓰기 작업이 중단될 수 있음. 

### 복제 구조 종류

##### 싱글 레플리카 

![](https://i.imgur.com/ALFKP2f.png)

- 가장 기본적인 복제형태
- 한대의 Primary 서버에서 한대의 Secondary 서버로 데이터를 복제
- 데이터 백업, 읽기 쿼리 부하 분산

##### 멀티 레플리카 

![](https://i.imgur.com/gzlmLt7.png)

-  여러대의 서버로 복제.
- 쿼리 부하를 나누고, 백업용으로 처리 가능. 

##### 체인복제 

![](https://i.imgur.com/IxyUI5f.png)

- 복제가 연쇄적으로 이루어지는 형태
- 데이터 분산, 부하분산에는 좋은데 만약 오류생기면 연쇄적으로 오류. 
- 지연시간 증가 등의 문제가 있다. 

##### 듀얼소스

### 변경사항 복제되는 과정 (MySQL 기준)

- 1. 원본(Source)에 변경 사항 기록
	- 애플리케이션(백엔드)가 원본 DB에 쓰기작업을 요청
	- Source DB는 이 작업을 처리하고 변경되었다는 이력을 바이너리 로그라는 특수파일에 차곡차곡 기록한다. 

- 2. 복제본으로 로그 전송
	- Replica DB의 IO Thread (수입 담당)이 변경된거 좀 줘 라고 요청
	- Source DB는 Dump Thread (수출 담당)가 변경된 내용을 수입담당(IO Thread)에게 전달.
	- Replica의 IO Thread(수입담당)은 받은 내용을 릴레이 로그라는 임시 파일에 저장한다. 

- 3. 복제본에 변경사항 적용
	- Replica DB의 SQL Thread (적용 담당)가 릴레이 로그(Relay Log)에 새로 저장된 작업들을 순서대로 읽음
	- 그리고 그대로 실행.
	- 이러한 과정으로 동일한 상태로 만들어짐.
